CHAPTER 02 · 数据与训练

第 1 讲：数据怎样进入 ChemDual，YAML 怎样控制训练

先看阅读顺序。本讲的 Python/JSON/YAML 摘录来自本地作者原文件；行尾中文注释由我添加。原文件：conf/train_ChemDual_pretrain.yaml、conf/train_ChemDual.yaml、conf/predict_decompose.yaml、conf/export_ChemDual.yaml；数据文件位于 dataset/。

1. 一条数据是什么

用途。 LLaMA-Factory 读取“任务说明、输入、期望输出”三项。以下是作者公开的分子切分测试样本；由于它属于测试集，只能看结构或最后评估，不能拿去训练。

{
  "instruction": "Could you help me separate the molecule into its constituent parts?",
  "input": "CC1=NN(c2ccc(C)cc2)C(=O)[C@]12C(=O)C=CC[C@H]2c1ccc(C)cc1",
  "output": "[10*]N1N=C(C)[C@@]2(C(=O)C=CC[C@H]2[15*])C1=O.[16*]c1ccc(C)cc1"
}

逐行。 { / } 表示一个 JSON 对象；instruction 告诉模型要“拆分分子”；input 是待拆的分子 SMILES；output 是正确答案，. 把两个片段隔开，[10*] 等是 BRICS 切口标记。此处 @ / @@ 编码立体化学，不能随便删。

为什么这样写？ 训练时同一个语言模型可以用不同的 instruction 执行多种方向的任务。另一份公开测试文件的 instruction 是重组，输入是多个片段，输出是完整分子。其他方法。 可以用 prompt/completion、聊天消息或 CSV；对这个仓库，保持 instruction/input/output 最贴近作者配置。批量运行建议 JSONL（一行一条）或 Parquet 便于流式处理，但换格式须同步修改注册信息；“格式更适合大数据”不等于“结果能与作者数值直接比较”。

为什么这样写？ 这些配置把模型、数据、训练与验证参数交给成熟训练框架，作者无需重写优化器和分布式训练。其他方法。 自己写 PyTorch 训练循环可精确控制损失、采样和 tokenizer，但开发与调试量大；追求与仓库一致时先用同版本 LLaMA-Factory 更合适，之后如需定制再写自己的循环。为什么作者采用这个框架没有说明；从仓库来看，它减少了训练代码量，这只是合理推测。

第 2 讲：eval_chem_metrics.py 逐段读

原文件：evaluation/eval_chem_metrics.py。下方代码是原逻辑的分段摘录，中文 # 注释为教学说明；原文件本身未改。它的顶部注明部分代码源自 MolT5。输入是 JSONL，每行如 {"label":"CCO","predict":"OCC"}；输出是有效性、几种分子指纹相似度，终端还会打印一个叫 Accuracy 的值。

2. 逐行读预测，累计组分重合

用途。 把每条正确答案和模型预测变成 RDKit 分子，同时累加一个“组分部分命中”数。

def evaluate(input_file, morgan_r, verbose=False): # 定义评估函数
    outputs = []       # 存成功解析的 (正确分子, 预测分子)
    bad_mols = 0       # 记录出错行
    correct = 0        # 累计每行的组分重合比例
    total = 0          # 记录进入该计算的行数
    with open(osp.join(input_file)) as f: # 打开预测文件；单参数 join 等于原路径
        for line in f.readlines():        # 一次把所有行读进内存再循环
            try:                          # 下面任一步出错都跳到 except
                line = json.loads(line)   # 字符串 -> Python 字典
                gt_smi = line["label"]    # 正确答案的 SMILES
                ot_smi = line["predict"]  # 预测 SMILES
                correct += len(set(gt_smi.split(".")) & set(ot_smi.split("."))) / max(
                    len(set(gt_smi.split("."))), len(set(ot_smi.split(".")))
                )                         # 两边组件取交集 / 组件数较大的一边
                total += 1                # 这行先计入总数
                gt_m = Chem.MolFromSmiles(gt_smi) # 解析正确答案
                ot_m = Chem.MolFromSmiles(ot_smi) # 解析预测
                if ot_m == None:          # 预测无法解析
                    raise ValueError("Bad SMILES") # 主动抛出异常
                outputs.append((gt_m, ot_m)) # 合法预测留待计算指纹
            except:                       # 原代码捕获所有异常
                bad_mols += 1             # 出错行加一

逐行重点。 def 后是函数名和三个参数。outputs 仅装成功走到 append 的行；bad_mols 是所有异常数，既可能是非法预测，也可能是 JSON 坏行、字段缺失、零除等。correct 是每行一个 0–1 的分数再相加，不是完整反应完全匹配的 0/1 数。set(...) 去重，& 取交集，max(...) 防止短的一边让部分命中得分过高。例如答案 A.B、预测 A.C，得分 1/2；严格 Exact 应为 0。Chem.MolFromSmiles 返回 None 表示解析失败。if ot_m == None 可以更明确写作 if ot_m is None，原写法有效。

为什么作者可能这么写？ 对多个组分的逆合成答案，部分重合也能显示一点进展；这是根据代码效果的推测。全局评估更适合怎样写？ 数据很多时用 for line in f 流式读，内存不随文件行数增长。用 except (json.JSONDecodeError, KeyError, ValueError) as exc 和行号记录错误，避免所有问题都被当作“坏分子”。先检查 gt_m 与 ot_m，并区分“参考答案错误”和“预测无效”。若论文要的是 Exact，应另写明规则：原始字符串严格相等、规范化后的组分多重集合相等，或者按 benchmark 官方定义；这些指标不能混用。保留原算法的好处是最容易核对作者仓库输出，改成更严格规则的好处是指标含义更清楚，但数值不能直接对照原打印的 Accuracy。

    validity_score = len(outputs) / (len(outputs) + bad_mols) # 成功行 / 全部处理行
    if verbose:                         # 仅详细模式打印
        print("validity:", validity_score) # 有效性
        print(
            f"Accuracy: {correct:.2f} / {total} = {(correct / total):.2f}",
        )                               # 累计部分分 / 计数

逐行。 len(outputs) 是成功解析并入队的行数；分母再加 bad_mols。if verbose 控制打印。f-string 里的 :.2f 把数字显示成两位小数，可能掩盖小差异。correct/total 与 validity_score 分母的含义不同：非法 SMILES 往往已经执行了 total += 1，也累计了 correct，然后才被划入 bad_mols。**边界情况：**空文件会零除；gt_m 是 None 但 ot_m 有效时，此处仍算“有效”，后面的指纹函数可能报错。

其他方法。 明确列出 n_rows、n_valid_prediction、n_bad_json、n_bad_reference、n_exact，每个指标写分母。处理空文件时给出可读错误。长期实验建议这样做，因为回头能解释分数怎么来的；对齐原仓库时仍需保留原算法作单独字段。不能把这里打印的 Accuracy 直接写成论文表 1 的 EXACT，二者定义不相同，论文也没有在此脚本中实现严格 Exact。

4. 三种“长得像不像”的分数

用途。 把分子变成三套不同的“结构特征表”（指纹），比较预测与答案的相似度。

    MACCS_sims = []   # 收集 MACCS 相似度
    morgan_sims = []  # 收集 Morgan 相似度
    RDK_sims = []     # 收集 RDKit 路径指纹相似度

    for gt_m, ot_m in tqdm(outputs): # 每对有效分子都评估，显示进度
        MACCS_sims.append(
            DataStructs.FingerprintSimilarity(
                MACCSkeys.GenMACCSKeys(gt_m),  # 正确答案的 MACCS 指纹
                MACCSkeys.GenMACCSKeys(ot_m),  # 预测的 MACCS 指纹
                metric=DataStructs.TanimotoSimilarity, # 相似度公式
            )
        )
        RDK_sims.append(
            DataStructs.FingerprintSimilarity(
                Chem.RDKFingerprint(gt_m),    # 正确答案的路径指纹
                Chem.RDKFingerprint(ot_m),    # 预测的路径指纹
                metric=DataStructs.TanimotoSimilarity,
            )
        )
        morgan_sims.append(
            DataStructs.TanimotoSimilarity(
                AllChem.GetMorganFingerprint(gt_m, morgan_r), # 正确答案
                AllChem.GetMorganFingerprint(ot_m, morgan_r), # 预测
            )
        )

逐行怎么起作用。 三个空列表各收集一种分数。tqdm(outputs) 只加进度显示，不改变数据。每个 append 把这一对分子的得分加进去。GenMACCSKeys、RDKFingerprint、GetMorganFingerprint 分别用不同结构信息描述分子；morgan_r 是 Morgan 指纹的半径。TanimotoSimilarity 可以粗理解成两套结构特征的交集占并集的比例。RDK/MACCS 通过 FingerprintSimilarity 接受 metric= 参数，Morgan 直接调用 TanimotoSimilarity，这是因为两种 API 的调用写法不同；数学目标一致。

为什么三种？ 不同指纹关注的结构信息不同，单个相似度可能遗漏某些差异。其他方法。 可以用批量 RDKit API、并行进程或预计算参考分子指纹来加速大测试集；它们更适合重复评估同一测试集。原写法逐对计算直观、依赖少，方便初学者和小数据。换不同指纹类型、半径或 canonicalization 会改变结果，不能拿它与论文数字直接比较。

5. 求平均、返回结果和命令行入口

用途。 汇总三种相似度，并允许终端直接运行这个脚本。

        print("Average MACCS Similarity:", maccs_sims_score)
        print("Average Morgan Similarity:", morgan_sims_score)

1. 导入库并读取预测

用途。 加载文件解析、tokenizer 和五类文本指标所需的工具。

import argparse                         # 命令行参数
import json                             # JSONL 每行解析
import os.path as osp                   # 路径处理

from rouge_score import rouge_scorer    # ROUGE 指标

def evaluate(text_model, input_file, text_trunc_length): # 3 个输入参数
    outputs = []                         # 存 (正确答案, 预测)
    with open(osp.join(input_file), encoding="utf8") as f: # UTF-8 读文件
        for line in f.readlines():      # 所有行先读进内存
            line = json.loads(line)     # 单行 JSON -> 字典
            outputs.append((line["label"], line["predict"])) # 保存两个文本

逐行。 argparse 管 CLI；json 解析；osp 在这里也只是对一个路径调用 join；tqdm 显示进度；np 计算平均；其余库各负责一类指标。outputs 在循环后成为一组二元组。原脚本未捕获坏 JSON、缺字段或空文件错误。为什么这样写？ 文件全读出来便于后面分别计算 BLEU/METEOR 和 ROUGE。其他方法。 大规模运行可逐行读并边算可累积的指标；但 corpus BLEU 仍需保留或累计足够的 n-gram 统计，不能简单地把每行 BLEU 平均当作 corpus BLEU。原写法更短、更容易核对，小型测试集完全够用。

2. 用模型 tokenizer 切开答案

用途。 BLEU 和 METEOR 需要 token 序列，所以先把 SMILES 字符串切成 token。

    text_tokenizer = AutoTokenizer.from_pretrained(text_model, pad_token="<|eot_id|>")
    bleu_scores = []         # 原代码创建，但后续没有使用
    meteor_scores = []       # 每条 METEOR
    levenshtein_scores = []  # 每条编辑距离
    references = []          # BLEU 的参考答案列表
    hypotheses = []          # BLEU 的预测列表

    for gt, out in tqdm(outputs): # gt 是正确答案，out 是预测
        gt_tokens = text_tokenizer.tokenize(
            gt, truncation=True, max_length=text_trunc_length, padding="max_length"
        )                       # 把正确答案切成 token
        gt_tokens = list(filter(("<|eot_id|>").__ne__, gt_tokens))
                                # 删除等于结束/填充标记的 token
        out_tokens = text_tokenizer.tokenize(
            out, truncation=True, max_length=text_trunc_length, padding="max_length"
        )                       # 把预测也切成 token
        out_tokens = list(filter(("<|eot_id|>").__ne__, out_tokens))
                                # 同样删除结束/填充 token
        references.append([gt_tokens]) # BLEU 规定每条可有多条参考答案
        hypotheses.append(out_tokens)  # 对应一条预测
        mscore = meteor_score([gt_tokens], out_tokens) # 这一条的 METEOR
        meteor_scores.append(mscore)   # 加入列表
        levenshtein_scores.append(Levenshtein.distance(gt, out))
                                # 字符级编辑距离，不按 token 计算

逐行重点。 AutoTokenizer.from_pretrained 需要一个可用的本地 tokenizer/模型目录或可访问模型名；text_model 不是随便写的显示名称。指定 pad_token 为 LLaMA 的结束标记；随后用 filter 去掉这个标记。tokenize(...) 得到 token 文本列表；不能看到传了 padding 就断言 tokenize 的输出一定被补到固定长度，实际行为要看所装 Transformers 版本。references.append([gt_tokens]) 的双层方括号是 corpus BLEU API 要求：每个预测对应一组参考答案。Levenshtein.distance 是把一个原始字符串变成另一个至少要几次单字符插入、删除或替换。bleu_scores 是未使用变量，删掉不改变结果。

为什么用模型 tokenizer？ 与模型实际见到的 token 更接近，这是合理推测；仓库没有解释选择依据。其他方法。 用专门的 SMILES tokenizer 或字符级切分可让化学符号更直观，但 BLEU/METEOR 数值会变，不能与原评估混称。对两周内的严格核对，先固定同一 tokenizer 和版本；长期运行应把 tokenizer 的路径、版本和词表哈希写进结果文件。若作者的多尺度 tokenizer 不公开，文本指标即使脚本跑通也无法保证与论文完全一致。

3. BLEU、METEOR 与编辑距离

用途。 汇总 token n-gram 的匹配和字符串差异。

逐行。 bleu2 比较长度 1、2 的连续 token 片段，各权重一半；bleu4 比较 1–4 长度，各四分之一。corpus_bleu 看整个数据集，不等于逐行 BLEU 平均。接着打印两项。np.mean(meteor_scores) 对前面每条的 METEOR 求平均，最后打印。编辑距离在下段最后输出。为什么保留多项？ 一项高分未必说明完整答案正确，多个角度能描述输出差异。其他方法。 化学任务最重要的是另外计算规范化结构意义上的完全一致与有效性；BLEU/METEOR 只能作为补充。原指标方便与已有分子文本生成论文对照，结构指标更能回答“分子是否正确”，但其规则也需要固定。
